Metric definitions reviewed by the project owner, and a dashboard that never runs out of
requests on its demo links.

**Metric definitions** (each reviewed one by one; see [PLAN.md](https://github.com/GonzaSSH/dora-dashboard/blob/main/PLAN.md) §2)
- **Revert rule:** a revert now fails only the release that actually shipped what it
  reverts.
  - It is traced by commit ID, by pull request, or by title when a fix was copied to a
    maintenance branch.
  - A change reverted inside its own release fails nothing.
  - Reverts that can't be traced are listed in one collapsed note.
- **Rework rule:** rework now counts releases that fixed a detected failure. Counting every
  patch release gave 75–96% on five real projects, so that reading is kept only as a
  non-default setting.
- **Ratings:** "strong / weak" is shown only for the two directly measured metrics
  (deployment frequency, lead time). The three proxies show what moves them instead.

**Demo links**
- The examples (the test repository, angular/angular) load saved results with zero
  GitHub requests, clearly marked "Saved result from …". **Analyse** fetches live data.
- A "Refresh snapshots" workflow keeps them current.

**Other**
- A note when a period has fewer than 5 releases, instead of hiding thin numbers.
- The README's AI section is updated with DORA's 2025 findings.
- A Release workflow creates releases from `release-notes/`.

**Test repository:** a new case where one failure needs two fix releases. The expected
values were redone by hand in [EXPECTED.md](https://github.com/GonzaSSH/dora-dashboard/blob/main/sandbox/EXPECTED.md).
